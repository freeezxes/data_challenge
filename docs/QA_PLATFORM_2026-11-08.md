## Подробности и воспроизведение

### QA-01 · P2 · Задание сохраняется до валидации параметров

**Где:** `app/server.py:104`.

`POST /api/jobs {"dataset_id":"QA","votes":6}` возвращает 400, но в БД уже есть `status=running`, `done=failed=0`, `finished_at=null`. То же для `votes="bad"`. Исполнителя у этих заданий нет. `votes=0` вместо отказа возвращает 200 и запускает три прогона: `votes or self.config.votes` подменяет ноль.

**Влияние:** ложная бесконечная активность интерфейса; некорректные параметры могут запускать более дорогой режим.

**Исправление:** проверять типы/диапазоны, создавать client/evaluator и формировать допустимый список работ до записи задания; отличать `None` от нуля. Сбой постановки должен переводить созданное задание в терминальное состояние.

**Проверки:** `invalid_job_votes_6`, `invalid_job_votes_bad`, `invalid_job_votes_0`.

### QA-02 · P1 · Одна работа запускается дважды

**Где:** `app/server.py:98`, `public/js/pages/queue.js:68`.

Задержать первый ответ SDK, отправить второй `POST /api/jobs` на тот же диалог с `only_missing=true`. Оба запроса дают 200, сохраняются две оценки, SDK вызывается дважды. Фильтр учитывает готовые оценки, выполняющиеся работы не резервируют диалог. Кнопка очереди также остаётся доступной при запуске.

**Влияние:** повторные расходы, непредсказуемая последняя оценка; общий LiveBoard по `(dataset, conversation)` также разделяется между заданиями.

**Исправление:** атомарная резервация `(dataset, conversation, checklist)` на время работы, идемпотентность запуска; UI показывает уже выполняющуюся работу.

**Проверка:** `running_conversation_not_evaluated_twice`.

### QA-03 · P2 · Нет восстановления состояния после рестарта

**Где:** `app/server.py:58`, `app/store.py:189`.

Сохранить выполняющееся задание, открыть тот же файл БД новым `App`. Задание остаётся `running`, хотя потоки старого процесса уже не существуют. Воспроизведение моделирует сохранённое состояние прерванного процесса, без аварийного завершения рабочей платформы.

**Исправление:** на старте переводить незавершённые задания предыдущего процесса в `interrupted`/`error` или возобновлять их; показывать доступный повтор.

**Проверка:** `restart_recovers_abandoned_jobs`.

### QA-04 · P2 · Лимит истории скрывает активную работу

**Где:** `app/store.py:197`, `public/js/core.js:105`.

Создать выполняющееся задание, затем 20 более новых завершённых. `GET /api/jobs` возвращает 20 строк без `running`. Фронтенд использует именно этот маршрут и прекращает опрос, когда в списке нет активных заданий.

**Исправление:** активные задания возвращать независимо от лимита истории; опрашивать отдельно активные ID до их подтверждённого завершения.

**Проверка:** `polling_cannot_hide_older_running_job`.

### QA-05 · P1 · Коллизии ID приводят к потере текста

**Где:** `app/copilot.py:196`, `app/assist.py:154`, `app/store.py:166`.

Две тренировки, завершённые в одну секунду, получают одинаковый `practice-MMDD-HHMMSS`. После двух успешных HTTP-запросов и оценок в наборе одна запись, а история содержит две оценки, относящиеся уже к одному перезаписанному транскрипту. В тесте фиксируется только значение часов.

Второй независимый случай: два параллельных `/evaluations/{id}/variant` читают одинаковое число копий и оба создают `qa-chat~1`. Оба возвращают 200, сохраняется одна копия. `save_dataset` выполняет upsert текста, поэтому коллизия незаметна.

**Влияние:** потеря диалога и ложная связь старой оценки/доказательств с новым текстом.

**Исправление:** UUID/атомарная выдача ID, insert-only для новых тренировок и вариантов; транскрипт, к которому привязаны оценки, должен быть неизменяемым.

**Проверки:** `practice_unique_ids_same_second`, `concurrent_variants_do_not_overwrite`.

### QA-06 · P2 · Ошибка завершения имеет скрытый побочный эффект

**Где:** `app/copilot.py:193`, `app/server.py:515`.

Без ключа `POST /api/copilot/finish` даёт 400 «Не задан ANTHROPIC_API_KEY», но новый чат уже сохранён в `PRACTICE`. UI считает действие неуспешным и предлагает повтор. Аналогичный порядок у варианта: сначала создаётся копия, затем проверяется возможность запуска задания.

**Исправление:** либо заранее проверять возможность оценки, либо явно возвращать «чат сохранён, оценка недоступна» с ID и доступным повтором именно этой записи.

**Проверка:** `practice_no_key_atomic_failure`.

### QA-07 · P1 · Выбор версии теряет доступные результаты

**Где:** `app/server.py:202`, `app/server.py:575`, `app/operators.py:56`, `app/submission.py:63`.

Оценить один диалог версиями v8 и v9. Запросить аналитику, экспорт и операторов с явным `checklist=v8`. Результат: `n_evaluated=0`, экспорт `not_evaluated`, операторов 0, хотя оценка v8 хранится и видна в истории карточки. Код сначала выбирает `max(id)` без версии, затем отбрасывает v9. В официальной выгрузке применяется тот же порядок, там появляется ошибка другой версии.

**Исправление:** отдельный запрос «последняя оценка данной версии» с фильтрацией `checklist_key` до `max(id)`. Семантику последней попытки/последней успешной попытки определить явно и одинаково для всех представлений.

**Проверка:** `explicit_historical_version_views` (HTTP аналитики, экспорта, операторов; официальная выгрузка дополнительно проверена по коду).

### QA-08 · P2 · Разная семантика счётчиков

**Где:** `app/store.py:175`.

После успешной оценки добавить неудачную переоценку. `/api/state` сообщает `evaluated=1` — считает любую историческую успешную оценку. Очередь сообщает ошибку и 0 оценённых — использует последнюю попытку. Пользователь видит разные числа на главной и в очереди.

**Исправление:** общий запрос готовности или явно раздельные «есть успешная оценка в истории» и «последняя попытка успешна».

**Проверка:** `state_counters_match_latest_evaluation`.

### QA-09 · P1 · Редактируемая шкала фактически не поддерживается

**Где:** `cqa/derive.py:147`, `cqa/evaluator.py:87`.

У консультации c04 сохранить шкалу `0/50/100`, сохранив название. Сохранение и активация дают 200. Модель возвращает допустимый `answer="100"`, `facts="essential_closed"`. `derive` заменяет ответ на зашитое 20, нормализация падает: `c04: 20 — нет такой ступени шкалы`. Итог задания — `done_with_errors`.

**Влияние:** пользователь может обычным редактором создать принимаемую конфигурацию, по которой нельзя оценивать диалоги. Схожая зависимость есть у шкалы ведения и правил, распознаваемых по названию.

**Исправление:** derivation должна быть совместима со снимком настраиваемого критерия; применять специализированные правила только к явно совместимой конфигурации, остальное оценивать по текущей схеме/правилам. Не узнавать алгоритм только по подстроке названия.

**Проверка:** `editable_consultation_scale_evaluates`.

### QA-10 · P1 · Валидатор пропускает невычислимую шкалу

**Где:** `cqa/checklist.py:39`, `cqa/scoring.py:29`.

Сохранить две уникальные целые ступени `-1/0`. Это считается валидным чек-листом и становится активной версией. Расчёт для ответа 0 падает с `decimal.InvalidOperation / DivisionUndefined`, поскольку верхняя ступень — ноль. Отрицательные шкалы также не ограничены проверками диапазона итогов.

**Исправление:** валидировать математические предусловия шкалы до сохранения: положительный максимум, допустимый неотрицательный диапазон; проверять другие числовые поля на конечность и допустимость округления.

**Проверка:** `reject_scale_with_zero_maximum`.

### QA-17 · P2 · Потеря данных о неуспешных вызовах

**Где:** `app/server.py:122`, `cqa/evaluator.py:264`.

SDK возвращает `stop_reason=refusal` и ненулевой usage. Оценщик прикрепляет `calls` к исключению, но App сохраняет только текст ошибки. В результате job cost — 0, `/trace` содержит `calls=[]`, `usage=null`, хотя вызов состоялся.

**Исправление:** сохранять журнал/usage/cost неуспешных ответов отдельно от результата критериев; агрегировать расходы в finally и не считать «нет результата» эквивалентом «нет расходов».

**Проверка:** `failed_model_call_keeps_usage_cost_and_trace`.

### QA-18 · P2 · Аналитика занижает общие расходы

**Где:** `app/server.py:219`, `public/js/pages/analytics.js:24`.

Один диалог, три прогона: job cost по синтетическому usage — `0.0096`, аналитика «всего» — `0.0072`: прогрев кэша потерян. Также агрегируются только последние оценки, поэтому предыдущие платные переоценки не входят в «всего». В браузере расхождение видно между завершённым заданием и аналитикой.

**Исправление:** разделить «стоимость показанных оценок» и «все расходы набора»; расходы считать по журналу вызовов/заданий, включая прогрев, ошибки и повторные попытки.

**Проверка:** `analytics_total_cost_includes_cache_warmup`.

### QA-19 · P2 · Финальный флаг не согласован со списком нарушений

**Где:** `app/server.py:180`.

В исходной оценке c08=`yes`, violations=`["disclosure"]`. Проверяющий меняет c08 на `no`. Очередь возвращает `critical=false`, но `violations=["disclosure"]`: список берётся из исходного результата и продолжает показываться красным.

**Исправление:** список текущих нарушений согласовывать с финальными ответами; исходные показывать отдельно с явной исторической подписью.

**Проверка:** `withdrawn_critical_violation_removed_from_queue`.

### QA-20 · P2 · Вместо 404 обрывается соединение

**Где:** `app/server.py:683`.

`GET /qa-missing-file` приводит к `RemoteDisconnected`. То же для закрытых путей `/.env`, `/../app/store.py`, `/%2e%2e/app/store.py`, `/app/store.py`. Причина в серверном traceback: `send_error(404, "Файл не найден")` пытается записать русскую reason phrase в latin-1 и падает с `UnicodeEncodeError`.

В этих проверках содержимое закрытых файлов не выдавалось; это дефект HTTP-обработки, не подтверждённая утечка.

**Исправление:** стандартная ASCII reason phrase, локализованное описание в UTF-8 теле; проверка корректного ответа на отсутствующий файл.

**Проверка:** `missing_static_and_non_public_paths_return_404`.

### QA-21 · P2 · Недостаточный ключ кэша голоса

**Где:** `app/voice.py:264`.

Построить отчёт для локального WAV. Сохранить conversation ID и времена, поменять m4 с operator на client. Повторный отчёт целиком берётся из кэша и продолжает считать m4 репликой оператора. Ключ содержит ID, размер файла и времена, но не роли, текст или идентичность содержимого аудио.

**Исправление:** хэш нормализованного транскрипта, аудиосодержимого/устойчивой версии и версии алгоритма; атомарная запись кэша.

**Проверка:** `voice_cache_includes_transcript_roles`.

### QA-22 · P1 · Предотправочная проверка суфлёра имеет окно обхода

**Где:** `public/js/pages/copilot.js:104`, `public/js/pages/copilot.js:141`.

**Воспроизведено в браузере:** выбрать «Клиент из диалога», начать сценарий QA, заполнить ответ `Переведите мне на карту, я лично вложу` и сразу нажать Ctrl+Enter. Текст появляется в истории оператора, начинается ход клиента, промежуточного «Нарушение — отправить всё равно» нет. Проверка через `/copilot/check` запускается с debounce 250 мс, а send использует старое `s.instant`.

**Исправление:** проверять актуальный текст непосредственно при send и связывать результат с версией черновика; запретить отправку до завершения актуальной проверки. Осознанный override, если нужен тренажёру, должен требовать отдельного действия уже после показа нарушения.

### QA-23 · P2 · Черновик чек-листа теряется при SPA-навигации

**Где:** `public/js/pages/checklists.js:217`, `public/js/main.js:25`.

**Воспроизведено в браузере:** изменить название на `QA НЕСОХРАНЕННОЕ ИМЯ`, увидеть панель «Изменения не сохранены», нажать «Очередь», вернуться в «Чек-листы». Исходное имя восстановлено, предупреждения не было. `beforeunload` не защищает переходы по hash, а cleanup удаляет guard. Переключение роли также заново рендерит экран.

**Исправление:** guard внутри роутера и при переключении версии/роли либо сохраняемый черновик с явным восстановлением.

### QA-24 · P1 · Переход в карточку требует мыши

**Где:** `public/js/pages/queue.js:124`.

**Подтверждено DOM и кодом в браузере:** строка диалога содержит checkbox, обычные td и `onclick`, но не ссылку/кнопку, tabindex или клавиатурный обработчик. Единственный фокусируемый элемент строки выбирает её для оценки, открыть карточку с него нельзя.

**Влияние:** основной сценарий просмотра доказательств недоступен клавиатурой; WCAG 2.1.1 Keyboard.

**Исправление:** настоящая ссылка на ID диалога внутри таблицы; клик по остальной строке можно оставить дополнительным удобством. Проверить Enter, Tab и видимый фокус.

### QA-25 · P2 · Обрезанные значения аналитики на узком экране

**Где:** `public/js/pages/analytics.js:26`, `public/cqa.css:320`.

**Воспроизведено рендером:** при узком viewport панели критериев и каналов остаются в двух колонках из-за inline `grid-template-columns`. В блоке каналов значения `90` и полосы обрезаются. Измеренный CSS viewport — 487 px, правая граница `.hbar` — 499 px; панель скрывает выходящее содержимое. Запрошенный через инструмент размер был 390×844, но браузер сообщил фактическую CSS-ширину 487 — результат не выдаётся за физический тест на телефоне.

**Исправление:** вынести сетку в класс и переключать панели в одну колонку на узком экране; проверить ширины 390/487/720 и масштаб текста.

## Что этим аудитом не подтверждено

- Качество новых оценок реальной Claude, задержки и фактический биллинг провайдера: платный прогон не запускался.
- Живой API организаторов, актуальность подписанных URL, fallback/streaming конкретной версии SDK и реальные ограничения сети. LiveBoard проверен через частичный JSON, не через живой стрим Anthropic.
- Системные ограничения под длительной нагрузкой, отключение питания в середине SQLite-транзакции, миграции с произвольно повреждённой старой БД.
- Физические мобильные устройства, touch-жесты, полный WCAG-аудит и несколько движков браузера.
- Настоящая авторизация ролей: текущий продукт переключает демонстрационную роль на клиенте; это не рассматривалось как уже реализованный серверный RBAC.

Эти границы не отменяют воспроизведённые дефекты; они ограничивают заявления о полностью проверенной платформе.
